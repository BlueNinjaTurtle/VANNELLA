Voici le topo complet et propre de votre architecture système, divisé entre la partie IoT (l'émetteur) et la partie Web (le cerveau), mis à jour avec toutes les règles métiers dont nous avons parlé.PARTIE 1 : Le Topo IoT (Cisco Packet Tracer)Dans cette architecture, la partie IoT joue le rôle de périphérique d'acquisition et d'actionnement. Elle n'a aucune autonomie de décision : elle écoute l'environnement, transmet ce qu'elle voit, et exécute les ordres visuels ou sonores renvoyés par le serveur.1. Le rôle exact de la MCUÉcoute passive : Scruter en boucle le port numérique D0 (Lecteur RFID).Transmission immédiate : Dès qu'un badge valide est détecté, elle fige le traitement pour cette carte (anti-spam) et prépare une requête réseau.Rétroaction matérielle (Feedback) : Elle lit la réponse HTTP brute envoyée par le serveur :Si la réponse contient un signal positif (success ou AUTHORIZED), elle alimente le port D1 (LED Verte) pendant 1,5 seconde.Si la réponse contient un signal négatif ou échoue, elle alimente le port D2 (Buzzer / Siren) pendant 1,5 seconde.2. Le format et le type de requête envoyéeLa MCU utilise le protocole HTTP standard sous sa forme la plus légère et universelle :Méthode HTTP : POST (utilisée pour envoyer des données à traiter vers un serveur).En-tête (Header) crucial : Content-Type: application/json (indique au serveur PHP qu'on ne lui envoie pas un formulaire classique, mais un objet de données structuré).Format du Payload (Corps de la requête) : JSON brut (String).Exemple exact du Payload envoyé :JSON{
  "salle": "Salle_01",
  "uid_badge": "1002"
}
PARTIE 2 : Le Topo Web (Restructuration de l'Application)Pour passer d'un simple fichier texte (historique_pointages.txt) à une véritable logique métier sans que le système ne s'effondre, l'application Web doit se restructurer autour d'une Base de Données Relationnelle (MySQL) et d'un Script d'arrière-plan.Voici comment organiser cette structure proprement :1. La Structure de la Base de Données (Le Schéma SQL)Pour gérer votre logique, 3 tables principales suffisent. Le fichier texte actuel (historique_pointages.txt) peut être conservé, mais uniquement comme un journal de secours (Log de bas niveau).Table professeurs :id (INT, Clé primaire)nom (VARCHAR)uid_badge (VARCHAR, Unique) $\rightarrow$ C'est la clé de correspondance avec l'IoT.Table salles :id (INT, Clé primaire)nom_salle (VARCHAR) (ex: "Salle_01")disponibilite (ENUM: 'Libre', 'Occupe') $\rightarrow$ Modifié en temps réel par les badges et les plannings.Table horaires_cours (Le Planning) :id (INT, Clé primaire)professeur_id (INT, Clé étrangère vers professeurs)salle_id (INT, Clé étrangère vers salles)heure_debut (TIME) (ex: "08:00:00")heure_fin (TIME) (ex: "10:00:00")date_cours (DATE)statut_cours (ENUM: 'En attente', 'En cours', 'Termine', 'Absent')2. La Nouvelle Logique de l'API (index.php ou Contrôleur Web)Dès que l'API reçoit le JSON {"salle": "Salle_01", "uid_badge": "1002"}, le script déroule l'algorithme suivant :Identification du badge :Requête : SELECT * FROM professeurs WHERE uid_badge = '1002'Si aucun résultat $\rightarrow$ Réponse : {"status":"error", "code":"UNKNOWN_CARD"} (Le Buzzer crie).Vérification de l'horaire et de la salle :L'API récupère l'heure actuelle (ex: 08:05:00) et la date du jour.Requête : Chercher dans horaires_cours le cours associé à ce professeur_id pour la date du jour, où l'heure actuelle se situe dans la plage horaire du cours.Cas A (Erreur de Salle) : Le prof a bien un cours prévu maintenant, mais la salle_id associée dans le planning ne correspond pas à la "salle" reçue dans le JSON.$\rightarrow$ Réponse : {"status":"error", "code":"WRONG_ROOM"} (Le Buzzer crie). Aucune modification en BDD.Cas B (Le Double Badgeage) : Le prof est dans la bonne salle, au bon moment, mais le statut_cours est déjà à 'En cours'.$\rightarrow$ L'API comprend que c'est un second scan involontaire. Elle ignore la modification de la salle, mais renvoie un message de succès à la MCU : {"status":"success", "message":"Deja valide"} (La LED Verte s'allume) pour ne pas stresser l'enseignant.Cas C (Validation Standard) : Le prof est dans la bonne salle, au bon moment, et le statut_cours est encore 'En attente'.Action BDD 1 : Mettre à jour horaires_cours $\rightarrow$ statut_cours = 'En cours'.Action BDD 2 : Mettre à jour salles $\rightarrow$ disponibilite = 'Occupe'.$\rightarrow$ Réponse : {"status":"success", "code":"AUTHORIZED"} (La LED Verte s'allume).3. La gestion automatique des 15 minutes de retard (Tâche de fond)Comme expliqué, l'API ne peut pas deviner l'absence d'un professeur si celui-ci ne badge pas. C'est un processus asynchrone qui doit s'en charger.Le mécanisme : Un script PHP indépendant (ex: check_retards.php) est configuré sur votre serveur Apache pour s'exécuter automatiquement toutes les minutes (via une Tâche Planifiée Windows ou un Cron Job sous Linux).L'algorithme du script :SQL-- Sélectionner tous les cours qui devaient commencer depuis plus de 15 minutes et qui n'ont pas démarré
SELECT * FROM horaires_cours 
WHERE date_cours = CURRENT_DATE 
  AND STATUT_COURS = 'En attente' 
  AND CURRENT_TIME > ADDTIME(heure_debut, '00:15:00');
Si ce script trouve des lignes correspondantes :Il bascule le statut_cours à 'Absent'.Il bascule la disponibilite de la salle concernée à 'Libre'.Ainsi, votre algorithme principal d'attribution de salles détecte immédiatement que la pièce est de nouveau éligible pour une autre promotion.4. La Libération de la salle en fin de coursSuivant votre logique de sécurité, la salle repasse à l'état 'Libre' automatiquement lorsque l'heure actuelle dépasse l'heure_fin spécifiée dans la table horaires_cours. Ce traitement est également géré par le script de tâche de fond qui nettoie les cours arrivés à leur terme.Synthèse de l'évolution de votre flux :[Badge RFID] 
    │ (Données brutes JSON)
    ▼
[API PHP (POST)] ───► [Vérification BDD (Profs/Horaires/Salles)]
    │                                 │
    │ (Réponse JSON Rapide)           ▼ (Mise à jour États)
    │                       ┌──────────────────────────────────┐
    ▼                       │ Salles: 'Libre' ou 'Occupé'      │
[MCU: LED ou Buzzer]        │ Cours: 'En cours' ou 'En attente'│
                            └──────────────────────────────────┘
                                      ▲
                                      │ (Scan chaque minute)
                            [Script Cron (15 min retard)]
Avec ce topo d'architecture, le système est parfaitement balancé : l'IoT gère le physique en temps réel, le Web centralise les données persistantes, et le script Cron gère le facteur temps.
